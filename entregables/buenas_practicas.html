DIPLOMA AI ENGINEER

Buenas Prácticas del Proyecto Integrador

Guía para obtener los mejores resultados · DMC Institute

Este documento reúne buenas prácticas recomendadas para los estudiantes que desarrollarán el Proyecto Integrador del Diploma AI Engineer. Aplicarlas incrementa la calidad técnica del entregable, reduce el riesgo de bloqueos y mejora la presentación final ante el jurado. Están organizadas siguiendo el ciclo natural de un proyecto de IA: planificación → datos → modelado → despliegue → presentación.

01

🎯 Planificación y alcance del proyecto

Definir el problema antes que la tecnología

Muchos proyectos fracasan porque los estudiantes empiezan eligiendo una tecnología (LLM, Rasa, Azure) y luego buscan dónde aplicarla. El orden correcto es el inverso: primero define el problema de negocio, luego elige la herramienta que mejor lo resuelva.

✅
Hazlo así: "Reducir el tiempo de atención a clientes de un call center mediante un chatbot que consulta las FAQ y escala casos complejos."
❌
Evita: "Queremos usar RAG 2.0 porque suena avanzado" sin un caso de negocio claro detrás.

Delimita el alcance (MVP primero)

  • Define un Producto Mínimo Viable que puedas terminar en las 12 semanas del curso.
  • Haz una lista de funcionalidades "nice to have" y déjalas para después.
  • Aplica la regla 80/20: prioriza lo que genera el 80% del valor con el 20% del esfuerzo.

Criterios de éxito medibles

Define desde el inicio cómo vas a medir que tu solución funciona: precisión, recall, tiempo de respuesta, satisfacción del usuario, reducción de costos, etc. Sin métricas, no hay manera de demostrar resultados.

💡
Tip: Escribe el objetivo SMART del proyecto en una sola oración. Si no cabe en una oración, el alcance está mal definido.
02

👥 Organización del equipo

Roles claros desde el inicio

Líder / PM

Coordina al equipo, comunica con el docente, gestiona el cronograma y las entregas.

Data / ML Engineer

Responsable del tratamiento de datos, entrenamiento y evaluación de modelos.

AI / Backend Developer

Implementa la lógica del agente, integra APIs, LLMs, RAG y orquesta el pipeline.

Cloud / DevOps

Maneja el despliegue en Azure, contenedores, variables de entorno y monitoreo.

UX / Presentación

Diseña la demo, slides, video y cuida la narrativa de la presentación final.

Herramientas de colaboración

  • Git + GitHub: trabaja con ramas (feature/*), haz Pull Requests y revisa código entre pares.
  • Trello / Notion / Jira: tablero Kanban con tareas asignadas y fechas.
  • Reuniones semanales: 30 minutos para sincronizar avances y desbloquear.
  • Canal de comunicación asíncrono: Slack, Discord o WhatsApp para dudas rápidas.
⚠️
Cuidado: No dejes que una sola persona concentre todo el código. Si esa persona falla, el proyecto se cae. Distribuye y documenta.
03

📊 Gestión de datos

Asegura los datos antes de empezar a construir

El error más común en proyectos de IA es asumir que "luego conseguiremos los datos". Si no tienes datos representativos el día 1, busca alternativas: datasets públicos (Kaggle, HuggingFace Datasets), datos sintéticos o APIs abiertas.

Calidad sobre cantidad

  • Explora tus datos con un EDA antes de modelar (nulos, duplicados, distribución, sesgos).
  • Para RAG, invierte tiempo en chunking y limpieza de documentos. Un índice sucio produce respuestas sucias.
  • Versiona tus datasets (DVC, MLflow o simplemente fechas y hashes en los nombres).

Privacidad y seguridad

⚠️
Nunca subas a GitHub datos reales de clientes, credenciales, ni API keys. Usa .env, .gitignore y datos anonimizados.
04

🧠 Modelado e implementación

Empieza simple, itera rápido

  • Implementa primero una baseline sencilla (regla fija, modelo pequeño, prompt básico) y mide su desempeño.
  • Sube la complejidad solo cuando la baseline esté funcionando end-to-end.
  • No intentes optimizar antes de tener el pipeline completo.

Selección de arquitectura

¿Chatbot?

Evalúa si necesitas Rasa puro, Rasa + LLM o RAG 2.0. Cada nivel agrega complejidad y costo.

¿Recomendador?

Empieza con filtrado colaborativo o bandits. Pasa a Deep Q-Networks solo si el problema lo justifica.

¿Generativo?

Primero prueba con prompt engineering. El fine-tuning (LoRA) viene después si el prompt no alcanza.

¿Azure?

Si el caso se resuelve con Cognitive Services, úsalos. No reinventes lo que ya existe.

Buenas prácticas de código

  • Usa entornos virtuales (venv, conda) y un requirements.txt fijando versiones.
  • Separa configuración (prompts, parámetros) del código en archivos .yaml o .env.
  • Modulariza: un archivo por responsabilidad (datos, modelo, API, frontend).
  • Aplica type hints, docstrings y nombres descriptivos.
  • Escribe tests mínimos para las funciones críticas.

Control de alucinaciones (si usas LLM)

  • Define prompts con instrucciones claras y restricciones ("responde solo con información del contexto").
  • Implementa un fallback: si el modelo no sabe, que lo diga, no invente.
  • Valida las respuestas contra el contexto (RAG) antes de devolverlas al usuario.
  • Registra logs de entradas y salidas para analizar casos problemáticos.
05

☁️ Despliegue y reproducibilidad

Piensa en producción desde el inicio

  • Contenedoriza tu solución con Docker para que funcione en cualquier máquina.
  • Despliega al menos un endpoint accesible: Azure Functions, Streamlit, FastAPI + Telegram, Hugging Face Spaces.
  • Incluye instrucciones en el README para que cualquiera pueda levantar el proyecto en menos de 10 minutos.

Monitoreo básico

Registra métricas simples: número de consultas, tiempo de respuesta, errores. Esto diferencia un prototipo de juguete de una solución seria.

💡
Tip: Una demo que el jurado puede probar en vivo en su celular vale más que 20 slides de arquitectura.
06

📝 Documentación e informe técnico

Documenta mientras construyes

No dejes la documentación para el final. Cada semana, al cerrar, escribe un párrafo sobre lo que hiciste, los problemas encontrados y las decisiones tomadas. El informe final será un ensamblaje de esos fragmentos.

Estructura recomendada del informe

  1. Resumen ejecutivo (1 página).
  2. Contexto y problema de negocio.
  3. Objetivos y métricas de éxito.
  4. Datos utilizados y preprocesamiento.
  5. Arquitectura de la solución (con diagrama).
  6. Implementación (tecnologías, decisiones clave).
  7. Resultados y evaluación.
  8. Limitaciones y trabajo futuro.
  9. Conclusiones.
  10. Anexos: enlaces al repositorio y video.

Un buen README vale más que 10 páginas de informe

  • Descripción corta del proyecto.
  • Arquitectura (diagrama).
  • Requisitos e instrucciones de instalación paso a paso.
  • Ejemplo de uso (con capturas o GIF).
  • Créditos al equipo.
07

🎤 Presentación y sustentación

Estructura de una sustentación ganadora (20 min)

  • 1 min: Hook inicial. ¿Por qué este problema importa?
  • 3 min: Contexto, problema y objetivos.
  • 4 min: Arquitectura y decisiones técnicas clave.
  • 6 min: Demo en vivo del prototipo (lo más importante).
  • 3 min: Resultados, métricas y validación.
  • 2 min: Limitaciones y próximos pasos.
  • 1 min: Cierre y llamado a preguntas.

Consejos de presentación

  • Ensaya al menos dos veces cronometrando. El tiempo siempre se va.
  • Ten un video de respaldo de la demo por si falla internet.
  • Todos los integrantes deben hablar: distribuye las secciones.
  • Usa pocas palabras por slide. Habla tú, el slide solo apoya.
  • Prepara respuestas para las preguntas obvias (escalabilidad, costos, seguridad, alternativas).
⚠️
Error clásico: pasar 15 minutos en teoría y no llegar a la demo. El jurado quiere ver funcionar tu solución.

✅ Checklist de entrega final

  • Repositorio en GitHub público o compartido con el docente.
  • README claro con instrucciones de instalación y uso.
  • requirements.txt con versiones fijas.
  • Archivo .env.example (sin credenciales reales).
  • Código modular, comentado y sin credenciales hardcodeadas.
  • Informe técnico en PDF (10–20 páginas).
  • Presentación (PPTX o PDF) revisada por todo el equipo.
  • Video demostrativo de 3 a 5 minutos subido a YouTube/Drive.
  • Demo funcional probada el día anterior en el mismo equipo que usarás.
  • Plan B documentado por si falla el despliegue en vivo.
  • Todos los integrantes preparados para hablar y responder preguntas.
  • Entregables cargados en la plataforma antes de las 12:00 del 06/07/2026.
!

🚫 Errores frecuentes que debes evitar

Sobreingeniería

Usar RAG + fine-tuning + Azure para un problema que se resolvía con un FAQ simple.

Demo en producción el mismo día

Desplegar la solución horas antes de la sustentación. Siempre falla algo.

Métricas ausentes

Presentar una solución que "funciona" sin números que lo respalden.

Código en un solo notebook

Entregar un .ipynb monolítico imposible de leer, probar o desplegar.

Credenciales expuestas

Subir API keys a GitHub. Revocación inmediata y mala imagen profesional.

Un solo integrante activo

Que un miembro haga todo y el resto solo aparezca en la sustentación.

Ignorar el feedback

No ajustar después del primer y segundo seguimiento. Los hitos existen por algo.

Olvidar el usuario final

Construir una solución técnicamente impresionante que nadie usaría en la realidad.
